# CLAUDE Contribution Guidelines

This document provides guidelines for AI assistants (specifically
Claude) contributing to the oRm package.

## Package Overview

oRm is a lightweight Object-Relational Mapper (ORM) for R that
simplifies database interactions through an R6-based framework. The
package provides declarative model definitions, relationship management,
and CRUD operations without requiring raw SQL.

### Core Architecture

- **Engine**: Database connection manager with multi-dialect support
  (PostgreSQL, SQLite, MySQL)
- **TableModel**: Table representation with schema management and CRUD
  interface  
- **Record**: Individual row operations with transaction support
- **Column/ForeignKey**: Field definitions with constraints and
  relationships
- **Dialect System**: Database-specific SQL generation

## Development Guidelines

### Code Style

- Use **4 spaces** for indentation; avoid tabs
- Prefer **snake_case** for functions and variables
- Use **PascalCase** for R6 class names (Engine, TableModel, Record)
- Document all public functions with roxygen2 comments
- Follow existing patterns for error handling and validation

### File Organization

- Core classes in `R/` directory with descriptive names
- Dialect-specific implementations in separate files (`Dialect-*.R`)
- Tests organized in `testthat/` with corresponding test files
- Vignettes provide comprehensive usage examples

### Documentation Standards

- All public methods must have roxygen2 documentation
- Include `@description`, `@param`, `@return`, and `@examples` sections
- Use `@seealso` to cross-reference related functions
- Document field attributes in R6 classes using `@field`
- **Never edit .Rd files** - these are auto-generated by roxygen2

### Testing Considerations

- Follow test-driven development: add or update the failing test first,
  confirm it fails for the intended reason, then implement.
- Follow existing test patterns in `tests/testthat/`
- Test files should mirror source file names (`test-Engine.R`, etc.)
- Run the suite with
  `Rscript -e 'pkgload::load_all("."); testthat::test_dir("tests/testthat")'`.
  A single file is much faster during iteration:
  `testthat::test_file("tests/testthat/test-Engine.R")`.
- The full suite takes several minutes; run it in the background rather
  than under a short foreground timeout.

#### Container-backed integration tests

PostgreSQL and SQL Server tests run against throwaway docker containers
and **skip silently** when the container, the driver, or docker itself is
missing. A green run that reports skips has not exercised those dialects
-- check the skip count before claiming dialect coverage.

- `tests/testthat/helper-postgres.R` and `helper-mssql.R` start a
  container on demand, and their `reg.finalizer(onexit = TRUE)` **removes
  it when the R session exits**. A container is therefore never left
  ready between sessions; each run pays the startup cost, and all tests
  needing it must run in one session.
- SQL Server additionally requires the `msodbcsql18` ODBC driver on the
  host and the `odbc` package. Without them the suite skips with
  "No ODBC driver for SQL Server installed".
- To start the containers manually (matching what the helpers do):

```bash
docker run -d --name orm_postgres_test \
  -e POSTGRES_USER=tester -e POSTGRES_PASSWORD=tester -e POSTGRES_DB=tests \
  -p 5432:5432 postgres:14-alpine

docker run -d --name orm_mssql_test \
  -e ACCEPT_EULA=Y -e 'MSSQL_SA_PASSWORD=oRm_Test_Passw0rd!' \
  -e MSSQL_PID=Developer -p 1433:1433 \
  mcr.microsoft.com/mssql/server:2022-latest
```

  SQL Server needs ~30s before it accepts connections, and the `tests`
  database must be created once:
  `IF DB_ID(N'tests') IS NULL CREATE DATABASE [tests]`.
- Dialect-specific behaviour deserves a dialect-specific test. Flushing
  is the worked example: Postgres recovers generated keys with
  `RETURNING`, SQL Server with `OUTPUT INSERTED`, and SQLite with a
  last-rowid lookup, so `.autoflush` is asserted in all three of
  `test-Dialect-postgres.R`, `test-Dialect-mssql-integration.R`, and
  `test-Dialect-sqlite.R` rather than only in `test-Engine.R`.
- SQLite reserves the `sqlite_` table-name prefix; name test tables
  something else or `create_table()` errors.

### Database Dialect Support

**CRITICAL**: Dialect-specific functions must NEVER be included in core
classes (Engine, TableModel, Record, Relationship, etc.). All
dialect-specific behavior must use the custom method dispatcher.

#### Method Dispatch System

oRm uses a custom method dispatcher
([`dispatch_method()`](https://kent-orr.github.io/oRm/reference/dispatch_method.md)
in `Dialect.R:39`) for dialect-specific behavior:

``` r

# Correct - uses method dispatch
qualify(engine, tablename, schema)
set_schema(engine, schema)
flush(engine, table, data, con, commit)

# Incorrect - adding dialect logic to core classes
if (engine$dialect == "postgres") { ... }
```

#### Implementing Dialect-Specific Functions

When extending database support: - Create new dialect file following
`Dialect-*.R` pattern - Implement dialect-specific methods using the
naming convention: `function_name.dialect_name` - Provide default
implementations with `.default` suffix - Add dialect detection logic in
`Engine$detect_dialect()` - Use
[`dispatch_method()`](https://kent-orr.github.io/oRm/reference/dispatch_method.md)
for all dialect-dependent operations

#### Available Dialect Functions

Core dialect functions that use method dispatch: -
[`qualify()`](https://kent-orr.github.io/oRm/reference/qualify.md) /
`qualify.dialect` - Schema-aware table name qualification -
[`set_schema()`](https://kent-orr.github.io/oRm/reference/set_schema.md)
/ `set_schema.dialect` - Set database schema context -
[`flush()`](https://kent-orr.github.io/oRm/reference/flush.md) /
`flush.dialect` - Insert records with RETURNING support -
`ensure_schema_exists()` / `ensure_schema_exists.dialect` - Create
schema if needed -
[`create_schema()`](https://kent-orr.github.io/oRm/reference/create_schema.md)
/ `create_schema.dialect` - Explicit schema creation

#### Example Implementation

``` r

# In Dialect-postgres.R
flush.postgres <- function(x, table, data, con, commit = TRUE, ...) {
    # PostgreSQL-specific implementation with RETURNING
}

# In Dialect-sqlite.R  
flush.sqlite <- function(x, table, data, con, commit = TRUE, ...) {
    # SQLite-specific implementation
}

# Default fallback in Dialect.R
flush.default <- function(x, table, data, con, commit = TRUE, ...) {
    # Generic implementation
}
```

### Transaction Handling

- Respect existing transaction state via
  `engine$get_transaction_state()`
- Use
  [`with.Engine()`](https://kent-orr.github.io/oRm/reference/with.Engine.md)
  for transaction blocks
- Default to auto-commit when not in active transaction
- Handle rollbacks gracefully with appropriate error messages

### Relationship Management

- Support standard relationship types: belongs_to, one_to_many,
  many_to_many
- Maintain bidirectional relationship references (ref/backref)
- Ensure proper foreign key constraint handling
- Use appropriate read modes based on relationship cardinality

## Git Workflow

### Commit Messages

- Use **imperative mood** (e.g., “Add support for”, “Fix bug in”,
  “Update documentation”)
- Keep first line under 50 characters
- Provide detailed explanation in body if needed
- Reference issues with `#issue-number`

### Branch Strategy

- Work on feature branches from `main`
- Use descriptive branch names (`feature/add-mysql-support`,
  `fix/transaction-rollback`)
- Keep commits focused and atomic

## Common Patterns

### Error Handling

``` r

if (missing(required_param)) {
  stop("Required parameter 'required_param' must be provided")
}

tryCatch({
  # operation
}, error = function(e) {
  # cleanup and re-throw
  stop("Operation failed: ", e$message)
})
```

### R6 Method Documentation

``` r

#' @description
#' Brief description of what the method does
#' @param param_name Parameter description
#' @return What the method returns
#' @examples
#' \dontrun{
#' # Example usage
#' }
method_name = function(param_name) {
  # implementation
}
```

### Database Operations

- Always use parameterized queries with
  [`DBI::dbQuoteLiteral()`](https://dbi.r-dbi.org/reference/dbQuoteLiteral.html)
- Quote identifiers with
  [`DBI::dbQuoteIdentifier()`](https://dbi.r-dbi.org/reference/dbQuoteIdentifier.html)
- Handle schema qualification consistently
- Respect connection pooling and persistence settings

## Package Dependencies

### Required Imports

- **DBI**: Database connectivity
- **dbplyr**: SQL generation and dplyr integration
- **dplyr**: Data manipulation
- **R6**: Object-oriented framework
- **pool**: Connection pooling
- **rlang**: Non-standard evaluation

### Suggested Dependencies

- **testthat**: Testing framework
- **knitr/rmarkdown**: Documentation
- **stevedore**: Docker testing
- **charlatan**: Test data generation

## Contribution Checklist

Before submitting changes:

Follow code style guidelines (4 spaces, snake_case, etc.)

Add roxygen2 documentation for public methods

Update existing documentation if behavior changes

Add or update tests, and run them (including the container-backed
dialect tests when the change touches dialect behaviour)

Check for proper error handling and validation

Ensure database dialect compatibility

Verify transaction handling is appropriate

Write clear, imperative commit messages

Update relevant vignettes if adding major features
